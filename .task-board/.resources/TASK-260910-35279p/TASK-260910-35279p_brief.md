## Finding (read it first)
`docs/security-audit-2026-09.md` R2 (Medium): `_snapshot_boundary_locked` scans
the full log prefix and rebuilds the Merkle root for every `/v1/records` page,
`/v1/log` page, `/v1/snapshot` fetch and every cursor validation; all reads
serialize on one `RLock`; with 10⁵–10⁶ entries the service approaches
self-inflicted DoS. This leaf covers the boundary side; `/health` is the
sibling's.

## Deliverable
1. Boundary lookups are O(1) per request for a committed `log_size`: persist
   (or maintain in a durable, crash-safe way) the boundary tuple
   `(log_size, head, merkle_root, created_at)` per committed boundary at
   append time — recommended: a `boundaries` table written in the same
   transaction as the append, backfilled once at startup for an existing log
   (part of the §5 startup verification, which already walks the chain), so
   `snapshot_boundary(max_seq)`, `boundary_available()` and the R1 carried-
   boundary field check read one row instead of recomputing. An incremental
   Merkle frontier is acceptable instead, if root-at-size queries stay O(log n)
   without rescanning. Justify the choice in the results.
2. The contiguity/hash-chain proof stays: startup verification unchanged
   (full walk once), append verifies the new entry against the current head,
   and the memoized rows are validated against the recomputed chain at
   startup (a mismatch fails readiness like any §5 mismatch — never trust the
   cache over the log). Invalidate/advance exactly on head advance.
3. Reads do not rebuild the tree: prove it with an instrumented counter (e.g.
   a store-level `merkle_hash_operations` counter or a monkeypatched hasher)
   in a test — repeated `/v1/records`, `/v1/log`, `/v1/snapshot` and cursor
   validations after one append perform zero Merkle recomputation; an append
   performs O(log n) (frontier) or O(1) row-insert work. Timing assertions are
   not acceptable as the proof (flaky on shared runners); operation counts are.
4. Concurrency: every existing concurrency/idempotency/recovery/restore
   conformance test stays green; the lock discipline does not weaken (state
   what is now read outside the write lock and why it is safe).
5. `CHANGELOG.md` Unreleased entry "R2: …" (this leaf's half); README
   operations note if the schema gained a table (migration on startup,
   idempotent).

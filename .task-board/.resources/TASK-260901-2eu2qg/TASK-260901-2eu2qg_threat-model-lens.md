## How to read this

Findings are ranked by **cost-of-being-wrong before expensive implementation**. Each carries severity, area, the exact spec quote, why it is a weakness, a concrete strengthening proposal (spec-text direction), and a MUST-before-impl flag. I did not re-litigate accepted decisions (no-templating, data-only profiles, launcher-not-mandatory, human-owned prompt-injection review) except where I found a **concrete** failure. Style nits omitted.

Two claims I attacked and they **held** — recorded so the next reviewer doesn't re-spend the effort:
- **Env-var injection boundary is tight.** Fragment names come from the closed registry (schema `env.propertyNames` enum = exactly the 4 vars); the only profile-derived value component is the profile-name segment, and the `identifier` grammar is `^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9_-])?$` — no separators, no traversal, no shell metacharacters, no quotes, no spaces. `--format shell` single-quote escaping over that grammar cannot be broken out of. **No finding.**
- **Umbrella dispatch cannot be steered by profile bytes.** environments §11 fixes dispatch input to operator argv + PATH; profile/marker/fragment data is excluded by construction. The residual is PATH poisoning, which is a *different* threat (T8), not a profile-influence hole.

## Ranked findings (cost-of-being-wrong order)

### 1. [CRITICAL — must-before-impl] `isolated` credential mode does not reproduce on the two most common surfaces (T2+T3)
**Area:** credential passthrough (environments §7.4 / manager §12.4 / decision §7).
**Quote:** "A profile × environment pair MAY be configured `isolated`: no passthrough, the tool authenticates fresh inside the managed home — the supported shape for genuinely separate accounts." + macOS row "none (Keychain is ambient)".
**Why it is a weakness — verified, not inferred:**
- **macOS claude_code:** the credential lives in a Keychain generic-password item keyed `svce="Claude Code-credentials"`, `acct="iv"` (the macOS user). It is *not* keyed by `CLAUDE_CONFIG_DIR`. Two claude profiles set `isolated` resolve the **same** item — company and personal accounts collide. The headline use-case ("a company profile on a company account beside a personal one") fails on the flagship tool+platform.
- **Linux claude_code / codex / pi:** passthrough is a per-file symlink (`.credentials.json`, `auth.json`). These tools refresh tokens by writing a temp file and renaming over the target — which **replaces the symlink with a regular file**. After the first refresh either the managed home diverges from the native home (stale token in one) or, if the tool follows the link, an "isolated" session writes through into the shared credential. Credentials are excluded from drift/hash (§7.4), so this is **silent**. This is precisely the atomic-rename-turns-links-into-files hazard.
**Cost of being wrong:** the entire account-separation value proposition is implemented, shipped, audited green — and does not actually separate accounts, while operators believe it does. Fixing after implementation means reworking the credential model, the marker, and the passthrough vectors.
**Proposal:** (a) State that macOS claude_code `isolated` is **unsupported in rev 1** — the tool provides no home-scoped auth — and gate it (`environment_isolated_unsupported`) rather than silently sharing. (b) For file-symlink passthrough, specify rename-replace behavior per adapter: passthrough by a **shared credential directory** the tool rewrites in place, or a documented rewrite-safe file target, and add a status check that detects a passthrough link that has become a regular file. (c) Add negative conformance vectors: isolated-on-macOS-claude refuses; a post-refresh delinked passthrough is reported non-current.
**MUST resolve before implementation starts.**

### 2. [HIGH — must-before-impl] `context-secret-material` × pin interaction is undefined — bypass or unescapable DoS (T4)
**Area:** profile audit (environments §9.1 / manager §12.6 / §7).
**Quote:** "profile installation is always strict… a profile carrying such a finding fails installation" and "no configuration, flag, or policy may downgrade the mode"; §7 "Pins record content hash… a verifiable finding at or above `fail_on` blocks in strict mode."
**Why it is a weakness:** the spec never says whether an operator content-hash **pin** overrides a `context-secret-material` finding. The curator reference impl resolves it one way — `decideWithPins`: `if pinned { return DecisionAllow }` short-circuits *all* findings — which means **any credential/injection smuggled into a profile is installable the moment an operator pins the hash** (and operators pin hashes routinely to get past false positives). The opposite reading (pins never override, per "no policy may downgrade") makes a **false-positive secret finding permanently uninstallable** with no escape — a deterministic detector over free-form markdown WILL false-positive (e.g., an example `AKIA…` in a doc module, a base64 blob), and there is no per-span waiver.
**Cost of being wrong:** either a live credential-exfil/injection path through the one always-on gate, or a capability that legitimate profiles cannot pass — discovered only when a real profile is blocked in the field.
**Proposal:** state explicitly that `context-secret-material` is **unpinnable** (a blanket content-hash pin does not clear it), and add a **scoped false-positive waiver**: an operator annotation naming the exact file+span with a reason, recorded in the audit record, so a mis-flagged legitimate profile installs without opening a blanket bypass. Reference impl must be reconciled to whichever the spec chooses. Add vectors: pinned-profile-with-secret still blocks; scoped waiver clears only the named span.
**MUST resolve before implementation starts.**

### 3. [HIGH — must-before-impl] opencode `isolated` is a false-isolation no-op; XDG seeding re-crosses the boundary (T1)
**Area:** opencode adapter (environments §7.1, §7.4).
**Quote:** "`opencode` | none (auth lives in the XDG data directory, which the config swap never touches)" and "the manager seeds it with symlinks to every entry of the operator's effective XDG config home except `opencode/`."
**Why it is a weakness:** opencode auth is under `XDG_DATA_HOME`, but only `XDG_CONFIG_HOME` is swapped. So a profile×opencode pair set `isolated` changes **nothing** about auth — the tool authenticates against the same ambient data dir regardless — yet the operator is told `isolated` means "authenticates fresh." Separately, seeding symlinks back to the real `~/.config` means the "isolated" managed parent still contains live links into the operator's actual config (git, gh, gpg configs), so any write reachable inside the managed opencode home (a hostile skill, a compromised session) has a path straight back to real config — the isolation the whole profile split promises is defeated for opencode specifically. And `XDG_CONFIG_HOME` is process-tree-wide: every XDG child of an opencode launch relocates.
**Proposal:** make opencode `isolated` **refuse** (or hard-warn as unsupported) since it cannot isolate auth in rev 1; narrow seeding to a documented allowlist rather than "every entry except opencode/"; explicitly state XDG_DATA/STATE are unmanaged so operators don't assume the data-dir is isolated. Add a status/`env status` line naming the ambient auth dir for opencode.
**MUST resolve before implementation starts** (it changes the adapter's isolation contract and its vectors).

### 4. [HIGH] System-prompt-class modules enter with no install-time signal (T5)
**Area:** audit surfacing (decision §2, environments §9.1, §5.5).
**Quote:** "a system-prompt override is the sharpest instruction surface a profile carries" (decision security impact) — yet §9.1 adds only `context-secret-material` and defers intent to "human prompt-injection review."
**Why it is a weakness:** a `class:system` `replace` module reaches `--system-prompt-file` (claude/pi) or `model_instructions_file` (codex, full replacement) / `GEMINI_SYSTEM_MD` (gemini). The install-time audit produces **no distinct finding** that a profile — or a composed overlay pulled in by machine config — carries system-prompt content. The only warning is at launch, only under opt-in (except pi's unconditional file channels). A composed overlay can therefore introduce system-prompt bytes that no one acknowledged at install. Human prompt-injection review can't happen if nothing flags that there's system-prompt content to review.
**Proposal:** add a REQUIRED, always-`warn`, never-`fail_on` audit surfacing class `context-system-module-present` (analogous to the existing `script-command-declared-only` surfacing classes), naming each `class:system` module and its selector. It guarantees provenance visibility for the sharpest surface without blocking. Cheap, and closes the "entered silently" gap.
**Follow-up acceptable** only if the launcher/warning path is the sole channel — but composition makes install-time the right place; recommend before impl.

### 5. [HIGH] Enterprise cannot lock composition or mandated skills against a shadowing overlay (T6)
**Area:** composition + system config (environments §6, manager §1).
**Quote:** §6 "when two chain members declare the same skill, the declaration from the profile that precedence favors wins… a version divergence… is reported as a warning"; §1 "`locked` contains only `audit_registries`, `disable_builtin_registries`, `allowed_sources`, and `audit`."
**Why it is a weakness:** default precedence is `later-overrides-earlier` and an overlay is "typically the operator's refinement." So a personal overlay declaring the same skill name as a company-mandated skill **wins and shadows it**, with only a warning — no block, no non-overridable marker. And composition, current-profile, and per-target participation are all machine-config that system config **cannot lock**. An enterprise that ships a base profile cannot enforce "these skills are not overridable" or "this profile must be current" — the two things a managed fleet most needs.
**Proposal:** add a lockable composition policy to §1 `locked` (e.g. `composition`, `require_current_profile`), and/or a profile-declared non-overridable skill class the org registry can require, so a personal overlay cannot silently down-version a mandated security skill. If enterprise fleet management is a rev-1 goal this is must-before-impl; if deferred, say so explicitly in the phasing table (it currently isn't mentioned).

### 6. [MEDIUM] `env resolve` repair lock + launch-time integrity are unstated (T9)
**Area:** resolution/repair (environments §10.1, §12.5, §8.2).
**Quote:** §12.3 `profile use` runs "under the manager-home mutation lock"; §10.1/§12.5 repair "repairs it from the store when it is not" — **no lock cited**. §8.2 "The marker is a record, not a signature: it MUST NOT be used as an authorization token or provenance proof."
**Why it is a weakness:** `env resolve` is called by launcher/ax on every launch and resume, potentially concurrently for multiple sessions of one profile, and it *mutates* (repairs surfaces). Without an explicit lock, two resolves race to repair one managed home, or a repair rewrites a surface a live session is reading. And because the marker is explicitly not a signature, nothing binds integrity at launch: any same-user process can tamper with the managed home between repair and the child's read (managed homes are new user-writable state roots). Drift is only caught at `status` time, out of band.
**Proposal:** require `env resolve` repair to acquire the mutation lock (or a documented per-home lock), and record the repair→child-read TOCTOU as a known accepted residual, mirroring launcher §9's probe→exec race. Consider a launch-time surface-hash recheck as the launcher's cheap integrity step.

### 7. [MEDIUM] Xcode secondary target: `auto` silently writes a foreign-app security surface; MCP/commands stay ungoverned (T10)
**Area:** secondary fixed-home targets (environments §7.6).
**Quote:** "a machine with it re-materializes the target on every install, `use`, and `sync`" and "The embedded hosts' own files (`.claude.json`, `commands/`, `config.toml`, caches) are unmanaged in revision 1 and MUST NOT be written."
**Why it is a weakness:** under default `auto`, installing an *unrelated* profile silently rewrites the Claude/Codex agent embedded in Xcode's support directory — a security-sensitive context surface inside another application's private dir — on operations the operator didn't aim at Xcode. Meanwhile the embedded agent still executes whatever MCP servers (`.claude.json`) and `commands/` are present, none of which are audited or governed. An operator who pins a company profile to the Xcode target reasonably believes that agent is governed; its MCP/commands are not.
**Proposal:** `auto` should probe-and-report but require one-time explicit consent before the **first** write into a foreign-app dir; `env status` must state plainly that the embedded host's MCP + commands are unmanaged/ungoverned so the governance gap is visible, not assumed-closed.

### 8. [MEDIUM] Umbrella provider PATH poisoning by profile-scoped skill material (T8)
**Area:** umbrella discovery (environments §11) × global/skill bins (cli/curator.md, manager §5).
**Quote:** §11 "resolves to an executable named `curator-<name>` on `PATH`… Dispatch input is operator argv and `PATH` alone."
**Why it is a weakness:** profile-scoped skills materialize executables and Curator publishes global forwarding shims into a user-bin dir on PATH. Nothing in §11 forbids a managed/skill-published bin directory from **preceding** the real launcher on PATH or from containing a `curator-run`/`curator-session`. A compromised or hostile skill closure that lands `curator-run` earlier on PATH gets the next `curator run` to exec it with the operator's full environment. The profile-influence boundary correctly blocks profile *bytes* from steering dispatch, but not profile-*materialized files* from poisoning the PATH the dispatch trusts.
**Proposal:** resolve umbrella providers from a fixed trusted location or verify their identity before exec; explicitly forbid managed/skill bin dirs from shadowing `curator-*` names and from preceding system dirs in the activation PATH. At minimum document the requirement so implementers don't inherit git's looser model here.

### 9. [MEDIUM] Onboarding backups: sensitive prior context retained forever, unscanned (T7)
**Area:** backups (environments §8.3, §12.7).
**Quote:** "A backup, once written, is never overwritten… Backups are outside every surface hash and are never garbage-collected by revision-1 rules."
**Why it is a weakness:** a hand-maintained CLAUDE.md/AGENTS.md commonly holds secrets and proprietary context. Onboarding copies it into `.agent-environment-backup/` where it lives permanently, is never scanned by `context-secret-material` (backups aren't profile snapshots), never GC'd, and outside all hashing. `environment_backup_exists` failing rather than overwriting can also wedge a re-run takeover. It's a durable, unmanaged secret store created by a security feature.
**Proposal:** define a retention policy and an explicit operator scrub command; surface backup presence and age in `env status`; keep them un-materialized/un-served (already true) and say so.

### 10. [MEDIUM] Resume drift defaults to silent context substitution (T11)
**Area:** ax integration (curator-spec §10; ax PR #1 §13.10).
**Quote (PR #1):** "A resolved profile pin that differs from the recorded `works.relux.curator.profile-pin` value is environment drift: the default behavior is to warn and continue with the freshly resolved fragment."
**Why it is a weakness:** a session started under `companyA@X` can resume under `companyA@Y` (moved branch, or overlay change) running **different** instructions — including different `class:system` modules — with only a warning. Because extension keys are "data only, MUST NOT alter semantics," the drift check is advisory by construction and the digest is unsigned. For security-relevant company-policy context, silent substitution on resume is the wrong default.
**Proposal:** default to **refuse** on drift when the composition chain carries any `class:system` module (strict there, warn-continue for pure root context); this is a small change to the recommended-behavior text in the pending ax PR, cheapest to make before that PR lands.

## Top 5 that MUST change before implementation starts

1. **Credential `isolated` mode (T2/T3, finding 1):** define macOS-claude and file-symlink rename semantics; today the account-separation claim does not reproduce on claude/macOS and self-destructs on first token refresh elsewhere.
2. **`context-secret-material` × pin (T4, finding 2):** pin either bypasses the one always-on gate (reference-impl behavior) or makes false positives unescapable. Resolve to unpinnable + scoped waiver.
3. **opencode `isolated`/XDG seeding (T1, finding 3):** it's false isolation (auth never swapped) and the seed links re-cross the boundary. Refuse or redefine before freezing the adapter contract.
4. **System-module install-time surfacing (T5, finding 4):** the sharpest surface enters with zero acknowledgement; add the always-warn provenance class before the audit vectors freeze.
5. **Enterprise lockability of composition/mandated skills (T6, finding 5):** a personal overlay silently shadows a mandated skill and system config can't stop it. Decide lockability now or explicitly declare fleet-enforcement out of rev-1 scope.

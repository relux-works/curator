## Settled decisions (do not reopen)
- **Enforcement point = service startup, when a checkpoint is configured.**
  The checkpoint interchange object is a signed `registry-snapshot-v1`
  (the profile already produces them). A conforming service accepts an
  operator-supplied checkpoint at start (working name `serve --checkpoint
  <path>`; the profile names the capability, not the flag spelling, as
  "startup checkpoint comparison") and, AFTER the §5 startup integrity
  verification and BEFORE it binds its listener or reports ready, verifies
  the checkpoint signature against its accepted signing keys (the staged
  rotation set) and compares the live boundary with it:
  live `version`/`log_size` below the checkpoint → refuse
  (`restore_below_checkpoint`); equal version with different `head`,
  `merkle_root` or `log_size` → refuse (`restore_inconsistent_with_checkpoint`);
  above the checkpoint → serve only if the live log reproduces the
  checkpoint boundary at its `log_size` (head and Merkle root at that
  prefix), else `restore_inconsistent_with_checkpoint`; checkpoint that
  fails signature verification → refuse (`checkpoint_signature_invalid`).
  Refusal = non-ready, writes disabled, no automatic truncation or repair —
  the operator recovers the missing verified suffix or keeps the service
  unavailable (existing §6 wording).
- **Without a configured checkpoint** the service starts (no behaviour
  change — rollout is direct, impact row "R3/P2" in the campaign table is
  "under the hood") but MUST record the posture: startup diagnostics/audit
  log carry `checkpoint_not_configured`; with one, they carry the compared
  boundary (version, log_size, head) and the outcome. No change to the frozen
  `health-response-v1` schema; `/health` text says a refused comparison is a
  non-ready condition like a failed §5 verification.
- `verify-backup`-style offline comparison stays as the operator procedure
  for candidate backups; the profile names both places and says which one
  is normative for "before the service becomes ready".
- Closed diagnostics: exactly the four codes above, spelled identically in
  §6 text, a diagnostics table (add one to the profile in the style of the
  protocol documents if §6 has none), the vectors and the CHANGELOG.

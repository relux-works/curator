## Recommendation

Keep mandates' owner-confirmed pins and consumed-ID ledger outside Curator managed homes, keyed by a stable consumer identity. A passwd-home root is compatible with the inspected local launch path. Prefer an explicitly configured operator state root if custom XDG layouts must be supported: resolve it before managed overrides, then persist the choice. Passing an absolute `MANDATES_MANIFEST` is useful as a discovery pointer, but neither the pointer nor its contents can confer trust. Reuse waggle's proposed formats selectively; there is no shipped waggle/curator-trust pin-store implementation to depend on.

**Key findings:** child `XDG_STATE_HOME` will be a managed location for Muse; a generic new fragment field or env name is invalid in existing closed schemas; tagged Curator still emits v1 while main emits v2; launcher main already accepts candidate v3; Decisions 0019/0021 are adopted direction, with runtime migration still outstanding in the inspected launcher.

## Q1 — Where should per-consumer trust state live?

**Shipped and implemented:** Curator does not move the Unix account home to implement managed homes. Claude/Codex get `CLAUDE_CONFIG_DIR`/`CODEX_HOME`; Pi gets `PI_CODING_AGENT_DIR`; OpenCode gets `XDG_CONFIG_HOME` pointing to a managed parent [S1, C1]. Managed paths are `<manager-home>/environments/<profile>/<environment>` (with an `opencode/` child for its actual tool home). The default manager home is `~/.curator`, but `CURATOR_CONFIG` can change the config path, and the manager home is its directory [C1, C2]. Consequently neither a profile directory nor the manager-config directory is a stable per-agent identity store by contract.

Managed tool homes intentionally accumulate the tool's own sessions, trust records and approvals separately from the native home [S2, C3]. That is native harness state, not a blessed universal mandates state directory. A per-profile tool trust seed or credential passthrough does not make third-party authorization state stable across profiles. The inspected fragment vocabulary has no consumer identity or external trust-state-root member [S3, L1]. **No Curator-blessed per-consumer mandates directory was found in these contracts.** This is a bounded contract finding, not a claim that every possible external component lacks a store.

**XDG distinction:** in v2/OpenCode, data/state remain ambient and only config moves [S1]. In v3/Muse, launcher main accepts four managed parents: `<home>/config`, `/data`, `/state`, `/cache`, with no `HOME` override [L2, V1]. Candidate prose explicitly says this affects XDG-conforming child processes and OpenCode's ambient rule does not apply to Muse [V2]. Curator main at the pinned revision cannot itself emit Muse v3; the launcher support is landed source against a spec candidate. Thus saying either “Curator relocates HOME” or “Curator never rewrites XDG state” without adapter/version qualification is incorrect.

**UID/passwd answer for D20:** the inspected direct launcher launches a normal child with composed environment and working directory. Its `SysProcAttr` sets process-group/terminal controls, not credentials or a chroot [L3]. There is no passwd rewrite or UID virtualization in this path. This supports `getpwuid` for current same-account local launches; it is not a promise about a future host, container, NSS implementation or separate agent OS account. In tracked mode the launcher calls `ax`; the child's inherited environment belongs to the destination terminal backend [L4]. This research does not establish that backend's UID/passwd behavior. Curator-trust itself proposes separate agent accounts later [T2], where the agent's passwd home would no longer identify the human operator.

**Proposed location and tradeoffs:**

| Choice | Benefit | Cost / required rule |
| --- | --- | --- |
| `<passwd-home>/.local/state/mandates/consumers/<encoded-stable-identity>/` | Smallest viable default; independent of `$HOME`, config-home and Muse XDG swaps. | Ignores a custom operator XDG state root; account/home migration needs explicit migration; same OS account can still alter files. Fail if passwd lookup fails rather than falling back to `$HOME`. |
| `<operator-state-root>/mandates/consumers/<encoded-stable-identity>/` | Supports operator-selected absolute paths and custom XDG layouts. | Capture operator `XDG_STATE_HOME` before overrides, or use an operator-controlled absolute mandates setting. Persist the selected root; do not recompute it from a managed child's environment. Reject roots within managed homes and report drift instead of silently selecting another store. |
| Managed profile/tool home | Convenient per-profile storage. | Fails the requested continuity guarantee: profile changes select different pins/consumption state. Not recommended. |

The XDG standard defines state as persistent across restarts, defaults it to `$HOME/.local/state`, requires absolute XDG paths, and distinguishes it from cache/runtime storage. Here substituting the passwd-home for that default is an intentional mandates safeguard, not a claim that XDG specifies `getpwuid`. See [XDG Base Directory Specification §3](https://specifications.freedesktop.org/basedir/latest/#variables).

Recommend the passwd-home default for v1, with an explicit persisted operator-root override if needed. Use a stable registered consumer identity, not a launch/session ID, provider config directory, profile name or mutable display slug. Encode identity safely and isolate multiple consumers sharing the same OS user; the OS uid alone is not the consumer identity. Require owner-only access, explicit initialization/rebinding, durable serialized consumption, and backup/restore rules that do not erase consumption history. Missing, unreadable or corrupt established state must not trigger silent empty-store bootstrap. Those are recommendations for mandates, not implemented Curator guarantees. Directory placement protects continuity; it does not create a security boundary against a process of the same OS user [T2].

## Q2 — Carry the manifest path or sources in launch context?

**Current contract:** no `MANDATES_MANIFEST`, mandates sources, pin-store path or issuer trust member exists in the fragment. V2 is a closed top-level object; its `env` permits exactly one registry home variable [S3]. Candidate v3 admits four variables only for Muse and still closes the top level [V1]. The production launcher parser rejects unknown members and uses the closed adapter-specific env set [L1, L2]. Curator's builder calls the boundary check before emission: fragment env paths must remain under the managed environments root [C4, S4]. Therefore injecting a project manifest into `fragment.env`, adding a top-level field to existing v2/v3, or using MCP `env_names` to invent a literal path violates the current contract. MCP passthrough names only request existing operator values; they do not specify values [S4].

**Recommendation:** permit an operator/launch-owner selected absolute `MANDATES_MANIFEST` as a discovery pointer, especially when the agent's later cwd changes. Keep bounded cwd discovery as a fallback when no pointer was supplied. A supplied but unreadable/invalid manifest should produce an error; do not silently rediscover something else. Validate the manifest under mandates' rules, and verify its declarations against the already confirmed pins. A pointer, expected issuer hash, source URL or checked-in manifest must never bootstrap issuer trust. An explicit pointer gives reproducible discovery; cwd-only discovery is simpler but changes with cwd and parent layout. Passing sources directly duplicates the manifest merge/resolution logic, so prefer a path unless there is a specific snapshot/replay requirement.

The local untracked path inherits the plan environment, then overlays only owned literals, fragment env and engaged channels [L3, L5]. An operator exporting the proposed variable may therefore get ordinary inherited delivery; this is **not** Curator-managed manifest selection or a guaranteed tracked launch contract. Tracked transport serializes composed owned literals and MCP lookup names, not arbitrary inherited variables [L4]. Do not rely on incidental inheritance for tracked sessions, resumes or launches on another host. If pointers refer to local paths, resolve them on the destination host; if replay requires exact declarations, define a content digest and retention policy separately from trust.

D20's “stop the manifest walk at passwd home” is a reasonable ancestor ceiling but needs a rule for repositories outside that home: that directory will never be encountered in an upward walk. Use explicit project/product discovery boundaries there. Do not equate the discovery ceiling with the trust-state root.

**Who owns integration:** mandates owns manifest semantics, pins and consumer identity. Curator-spec maintainers own fragment prose/schema/vectors and any new revision [S5]. Because old readers reject additions, a fragment field requires a new version token with compatibility/security review and positive/negative vectors; do not mutate v2 or the candidate v3. Decision 0018's closed additive versioning precedent applies [D1]. If the pointer remains outside the fragment as a launcher-owned env literal, no fragment-schema change is required, but a reviewed launcher/module input and tracked-plan contract is still needed; that input is not implemented today.

Decisions 0019 and 0021 were adopted on 2026-10-01 [D2, D3]. Their target is one harness construction site in `agents-management`, fragment consumers in `curator-run` and task-board children, and a host that only receives a composed plan. 0019 leaves context-member and environment-composition shape open. The inspected launcher still spells channels in `internal/composition` [L5]; adoption alone does not establish delivery of the new architecture. Future manifests integration belongs with those owners, with the consumer selecting the pointer and the launch plane consistently transporting it. Do not add parallel discovery or flag construction to the session host. Permission modes in 0018 are harness policy, not issuer enrollment or owner-confirmed mandates pins.

## Q3 — Reuse curator-trust/waggle issuer rosters or pin stores?

**Proposed forms exist; shipped implementations do not.** Both repositories explicitly state that nothing is implemented [W0, T0]. Their naming and design direction can inform mandates, but cannot be offered as an installed verifier API or working shared registry.

Waggle proposes project `.waggle/allowed_signers`, stock OpenSSH principals and namespace constraints, plus `.waggle/revoked`. Operator, orchestrator, worker and host principals have different powers. Roster changes must be confirmed against the version already in force rather than admitting their own signer [W1]. Enrolment evidence lives beside it in `.waggle/keys/<principal>/<fingerprint>.json`, and verifiers re-check evidence rather than accepting a stored verdict [W2]. These are a project authority roster and proposed enrollment record layout, not a definition of a per-consumer owner-confirmed PIN-store filesystem location.

Curator-trust proposes local OS-authenticated initialization of a board anchor; certified additional keys of the same person; confirmed roster changes for new principals; and revocation checks along certification chains [T1]. It distinguishes operator-owned stores from the future agents' OS account [T2]. It does not establish a Curator-managed-home consumer-state directory. Its coupon paragraph leaves expiry and unknown-outcome consumption open [T3]; the peer's fsync/reissue design is a mandates proposal, not already settled or implemented here.

Reuse the **format and policy concepts** where compatible: explicit issuer/host principals, public key fingerprints, namespace-restricted `allowed_signers` projections, signed enrollment evidence, and authoritative revocation checks. Keep mandates pins and consumed-ID state independently owned until a shared profile defines initialization, stable identity, authority, freshness, revocation and migration. An `allowed_signers` line can be a verifier input generated from confirmed pins; merely discovering a project's roster must not add pins. Existing namespace grants do not implicitly grant mandates' new type/role namespaces. Likewise an issuer's signed host declaration does not replace the consumer's trust decision.

Curator has separate audit-registry public-key configuration and source-signature policy [C5]. Those keys authorize audit records or context Git sources, not arbitrary owner-signed actions. Do not reuse them as mandates issuers without an explicit new authority policy. A shared board-less waggle roster provider could be a useful later integration, but needs governance/anchoring and is not shipped.

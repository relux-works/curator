## 1. The Go metadata classifier is now exhaustive

The `go` registry entry is declared complete, so its classification is fixed
here rather than deferred. New reference sections 4.2.1 through 4.2.4.

**Shared literal grammar** (4.2.1):

```text
goVersionLiteral = ^(0|[1-9][0-9]*)(\.(0|[1-9][0-9]*))?(\.(0|[1-9][0-9]*))?([a-z]+[0-9]+)?$
```

A match yields a base triple (absent components are `0`) plus a prerelease flag.
Comparison uses the base triple.

*Why the base triple is exact, not approximate.* Go's own order is
`1.21 < 1.21rc1 < 1.21.0` — a bare language version sorts below its own release
candidates, so canonicalizing both `1.21` and `1.21rc1` to `(1, 21, 0)` looks
lossy. It is not: the two orders can disagree only for a comparand strictly
between `1.21` and `1.21.0`, every such value is itself a prerelease, and Stage A
step 4 rejected a prerelease host before Stage B ran. The orders therefore agree
on every comparison Stage B can perform.

**`go` directive classifier** (4.2.2), ordered, first match wins, total: absent →
no assertion; release literal → base-triple compare; prerelease literal → same;
catch-all → `build_toolchain_metadata_mismatch`. It has **no** `forbidden`
class, and that is stated explicitly: its Go-defined value space is a version,
so a value containing a path separator is class 4 (unclassifiable), never
package influence.

**`toolchain` directive classifier** (4.2.3), ordered, total — seven classes:

| # | Class | Disposition | Outcome |
|---|---|---|---|
| 1 | absent | — | no assertion |
| 2 | value contains `/` or `\` | `forbidden` | `build_toolchain_package_influence_forbidden` |
| 3 | custom distribution, `go1.23.4-bigcorp` | `forbidden` | `build_toolchain_package_influence_forbidden` |
| 4 | `default` | `compared` | permitted, never honored |
| 5 | canonical release name | `compared` | base-triple compare |
| 6 | prerelease name, `go1.24rc1` | `compared` | base-triple compare |
| 7 | catch-all | `compared` | `build_toolchain_metadata_mismatch` |

Three previously open cases now have one outcome each, and each follows from a
rule already fixed rather than a new judgment:

- **`toolchain default` is permitted and never honored.** It means "do not
  switch", which is unconditionally what Curator does; it is the one metadata
  value that asserts Curator's own behavior, so rejecting it would fail a
  package for agreeing.
- **A custom distribution name is package influence, not a mismatch.** The
  suffix names *where* a toolchain comes from, which is exactly what section
  3.1 reserves `forbidden` for, and it is the `go.mod` analogue of
  `rust-toolchain.toml` `path`. Calling it a mismatch would assert "this claim
  is false about the resolved toolchain", inviting a later implementation to
  verify the claim by consulting the named distribution — reopening selection.
- **A repeated directive** in one file is the catch-all class, so Stage B is
  total over file shapes as well as values.

Supporting machinery: new section 3.1.1 defines **value classifiers** for a
field whose value space spans dispositions — ordered classes, `forbidden`
classes first, mandatory catch-all last, and a classifier may read nothing but
the field value and the already-resolved version. The disposition column records
`classified` for such a field. Section 4.2.4 records that `go.work` is
deliberately not a metadata source, because `protocol/core.md` section 4.2
already fixes `GOWORK=off`, so a workspace file cannot affect the build.

Grammar was taken from primary sources, not from memory: `go.dev/ref/mod`,
`go.dev/doc/toolchain`, and the on-host vendored `golang.org/x/mod/modfile`
(`ToolchainRE = ^default$|^go1($|\.)`,
`GoVersionRE = ^([1-9][0-9]*)\.(0|[1-9][0-9]*)(\.(0|[1-9][0-9]*))?([a-z]+[0-9]+)?$`)
plus `cmd/go/internal/gover.FromToolchain`, which strips a suffix introduced by
`-`, space, or tab and rejects a name containing a path separator.

## 2. Overlapping triggers are partitioned, not merely ordered

**Wire overlap** (reference 3.1). Partition by *what fails*, never by what a
value resembles:

| Input | Rejection |
|---|---|
| key outside the closed field set | existing unknown-field schema rejection (`protocol/core.md` §4: schemas 2–7 reject unknown fields; every wire object is `additionalProperties: false`) — no `build_toolchain_*` code |
| value in a closed-set field failing that field's grammar, including a `version` literal carrying a path, prefix, URL, mirror, track, or command | `build_toolchain_requirement_invalid` |

`build_toolchain_package_influence_forbidden` therefore **never fires on the wire
surface**; it is a Stage B code only. Deciding that a malformed literal is
"smuggled influence" rather than "malformed" requires inferring intent from a
byte string, and two conforming managers would infer differently. The canonical
grammar rejects `/usr/local/go`, `https://…`, `nightly`, and `go1.23.4` for one
checkable reason: none is `major.minor.patch`.

The "no such field may be added" half becomes an **authoring obligation with a
release gate** — `TASK-260728-2jaw7h` enumerates the build-command and
descriptor-target property names of every published schema version and fails on
a forbidden kind. A runtime code cannot enforce it, because a field that does
not exist produces no value to diagnose.

**Stage A overlap** (reference 4.1). Step 2 splits into three sub-steps with
disjoint triggers:

| Sub-step | Question | Failure |
|---|---|---|
| 2a declaration | is a root declared for this id by an admissible origin? | `build_toolchain_unavailable` — the only producer of that code |
| 2b origin trust | did the declaration arrive through a forbidden origin, or is the config state unprotected? | `build_toolchain_untrusted` |
| 2c shape | missing root, absent/non-regular/non-executable primary, wrapper or shim, primary outside the tree | `build_toolchain_untrusted` |

The partition is **declaration presence, not severity**, and it is total. A
declared-but-broken root — including a declared root that does not exist at all
— is always `untrusted`. Routing that to `unavailable` would make the reported
code depend on how far the manager got before failing, and would send "your
configuration points at nothing" to `host` guidance that says "install a
toolchain". The partition matches the guidance classes already assigned:
`unavailable` → `host` (obtain a toolchain), `untrusted` → `configuration` (fix
the configuration).

## 3. The diagnostic payload is a representable typed union

New reference section 5.1. The shape is **derived, not chosen**: a code carries
exactly the values established at the point it fires, and because the stage
steps are totally ordered, that set is a function of the code. No sentinels, no
optional-by-judgment members.

- Common and REQUIRED everywhere: `code`, `driver`, `toolchain_id`,
  `guidance_id`.
- `effective_requirement` present iff step 1 completed — absent in exactly
  `requirement_invalid` and `requirement_unsatisfiable`.
- `resolved_version` and `prerelease` present iff step 4 normalization
  succeeded — absent in exactly those two plus `unavailable`, `untrusted`, and
  `version_undetermined`. `prerelease_unsupported` carries both, because
  normalization *did* succeed and it is the flag that rejects.
- `source_ref` is not step-conditional. It appears exactly where the per-code
  table lists it — `requirement_invalid`, `metadata_mismatch`,
  `package_influence_forbidden`, and inside each `fragments` element — and
  nowhere else, because no other code is attributable to a single input.
- Per-code extensions are tabulated for all twelve.

The two impossible cases become representable:

- **`requirement_invalid`** carries `source_ref` plus a closed `violation`
  token (`not_an_object`, `unknown_id`, `id_not_primary`, `unknown_kind`,
  `missing_field`, `unexpected_field`, `version_literal_malformed`,
  `version_literal_prerelease`, `range_bounds_not_ordered`). It MUST NOT echo
  the offending value: the payload never reproduces an unvalidated package byte,
  which keeps package-controlled text out of manager output and keeps the
  payload bounded. Location plus token identifies the defect exactly.
- **`requirement_unsatisfiable`** carries `fragments` — the individually
  validated contributing requirements with their source refs, which *are*
  validated fragments and so are safe to reproduce — plus `conflict` naming the
  maximum lower bound, the minimum upper bound, and every source achieving each,
  in Unicode-scalar order of `source_ref`. The payload is therefore as
  source-order-independent as the intersection itself.

## 4. Catalog coverage and version transitions are unambiguous

**Coverage** (reference 6.3) is now defined *by* the selection function instead
of alongside it. An active exact entry covers its operating system; an active
`any` entry covers the rest. All three shapes are valid — `any`, `per_os`, and
**hybrid**. Forbidding hybrid would reject catalogs that already resolve
deterministically, and forcing full per-OS duplication for one platform note is
how a catalog goes stale.

The gate checks two properties per `(toolchain_id, reason)` pair:

1. **Resolution** — every registry operating system resolves to exactly one
   active entry.
2. **Reachability** — every active entry serves some request. An exact entry for
   an OS outside the registry `platforms` set is unreachable and fails; an `any`
   entry shadowed by exact entries for *every* OS is unreachable and fails.

Reachability is what keeps hybrid honest: fallback plus overrides is admitted,
dead entries and a never-selectable fallback are not.

**Version transitions** (new reference 6.2.1) resolve the append-only versus
`active`-flip contradiction by stating each against the catalog *version*. A
published catalog version is immutable in whole — no addition, removal, or edit,
including `active` and `superseded_by`. Every change is a transition from N to
N+1, and exactly four transitions are admissible: carry forward unchanged; add a
next revision or a new tuple's revision 1; retire with a successor (requires a
strictly greater revision of the same tuple in N+1, named by `superseded_by`);
and retire without a successor, admissible **only** when the tuple is no longer
required by the coverage gate — the only cause being that its platform or
toolchain left the registry. Inadmissible: removal, editing an immutable member,
reactivation, changing `superseded_by` on a still-active entry, and retiring the
last active entry of a required tuple.

So the entry set is append-only across versions and `active`/`superseded_by` are
one-way monotone. "Exactly one active entry per tuple" relaxes to "**at most**
one", because retirement without a successor is now a defined state.

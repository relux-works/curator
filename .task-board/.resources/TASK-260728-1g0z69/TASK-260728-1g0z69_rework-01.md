## Finding 1 — the Go entry weakened the manager-tested-family gate

**Fix: a manager-owned closed compatibility predicate on every registry entry.**

- New REQUIRED entry field `compatibility` (reference §1.1), fully specified in
  new §1.1.1: a closed set of release families the manager has tested against
  that driver's conformance vectors. Membership is **exact set membership, never
  an ordering test**, so a family merely ordered after a member is not a member.
- Family granularity is declared per entry; for `go` it is `(major, minor)`.
- The `go` entry (§1.2) now carries `compatibility` = families `{(1, 23)}`,
  which is the released `profiles/manager.md` §2.2 rule verbatim: tested 1.23
  family, extension only by testing, newer-but-unknown release rejected.
- Package data can neither widen nor narrow the set, and no requirement spelling
  can reach it. The requirement and the compatibility set are **independent**
  gates (§2.3): satisfying one does not imply the other.
- Stage A gains step 7 (§4.1) with a fixed evaluation order, so both gates stay
  reachable and the reported code is deterministic:
  - Go 1.22.0 → step 6 → `build_toolchain_incompatible` (below baseline)
  - Go 1.99.0 → passes step 6 under `at_least 1.23.0` → step 7 →
    `build_toolchain_untested_release`
- New twelfth diagnostic `build_toolchain_untested_release` (§5), carrying the
  resolved version and the admitted family set (manager-owned data, never
  package data).
- Because a conforming manager MAY admit more families than another, the set is
  a gate rather than a build input, so conformance vectors declare it as fixture
  input and stay deterministic across managers.
- Vectors: 7 (preserve — admitted family builds), 31 (reject — Go 1.99.0 with a
  satisfied `at_least` still refused), 32 (precedence — Go 1.22.0 reports
  `incompatible`, not `untested_release`), 57 (a compatibility-set change alone
  produces an identical cache key).

- Reference §6.1 gives an explicit twelve-row code → `reason` → `guidance_class`

## Finding 3 — guidance identifier lifecycle was not implementable

**Fix: an immutable revision component.**

- Grammar is now `toolchain.<toolchain_id>.<reason>.<platform>.r<N>` (§6.2),
  `N` decimal, no leading zeros, starting at 1, strictly increasing per tuple.
- Published IDs are immutable; a change of meaning, `primary_source` origin, or
  class creates the next revision of the same tuple, and the old entry sets
  `active: false` plus `superseded_by` pointing at it.
- `superseded_by` MUST name an existing same-tuple entry with a **strictly
  greater** revision, so the chain is acyclic and terminates at the single
  active entry. Retired entries are retained so an older diagnostic stays
  resolvable.
- Selection still resolves the *tuple* — exact `(toolchain_id, reason, platform)`
  active entry, else the `any`-platform active entry — and the emitted
  diagnostic carries the resolved revisioned identifier.
- Release gate (§6.3) additionally checks revision monotonicity, `superseded_by`
  well-formedness, and one-active-entry-per-tuple.
- Vectors 49, 50, 51, 52 cover the failure and resolution cases.
- Follow-on gap found while making totality real and closed in the same pass:
  selection keys on `toolchain_id`, but a
  `build_toolchain_requirement_invalid` can be raised *because* the declared
  `id` is absent or outside the closed set, leaving nothing to key on. §6.2 now
  states that such a diagnostic resolves guidance under the **driver's registry
  primary toolchain**, which is always known because the driver is resolved
  before its requirement is read; a driver with no registry entry never reaches
  a `build_toolchain_*` code at all. Without this, the totality claim had a hole
  at exactly the reason the reviewer flagged as uncovered.

## Finding 4 — package channel handling was contradictory

**Fix: the forbidden category is defined by surface, not by "any channel-valued
field".**

New reference §3.1 makes the split normative:

- **Surface 1, the manager-defined wire surface** (manifest build command,
  `skill-build.json` descriptor target): Curator owns the closed field set. No
  channel/track/path/URL/command/env field exists there and none may be added; a
  closed schema rejects unknown keys, and such a value smuggled into an existing
  field is `build_toolchain_package_influence_forbidden`. On this surface a
  channel is simply forbidden — there is nothing to compare.
- **Surface 2, source-ecosystem metadata** (read at Stage B): Curator does not
  own the field set, so each entry declares a closed disposition table giving
  every field it reads exactly one of `forbidden`, `compared`, `ignored`.
  `forbidden` is reserved for values naming **where** a toolchain comes from;
  channel/track values are `compared`, because refusing to honor them is exactly
  what makes them harmless. An undeclared field is `ignored`.
- **Precedence is fixed** (§3.1, §4.2): within Stage B for one command, all
  `forbidden`-disposition fields are evaluated before all `compared` fields, each
  group in Unicode-scalar lexical order of relative source path then field path;
  first failure wins. `rust-toolchain.toml` with both `path` and
  `channel = "nightly"` is therefore **always**
  `build_toolchain_package_influence_forbidden`.
- Channel classification is now deterministic (§4.2 channel table): a
  canonicalizable version literal is an `at_least` assertion; `stable` is
  permitted and never honored (it asserts exactly the release-only property v1
  already enforces, and rejecting it would fail nearly every real package while
  proving nothing); `beta`, `nightly` and dated channels are a mismatch because
  they assert a prerelease host v1 never resolves; anything else is a mismatch,
  never a default and never a selector. This replaces the previous blanket
  "`stable`, `beta`, `nightly`, or a dated channel → mismatch" row.
- Stage B classification cases take the resolved version as fixture input, so
  reserved-toolchain disposition vectors need no Rust/Swift/Kotlin host.
- Vectors: positives 10, 11; negatives 35, 36, 37, 38, 39, 40 (precedence),
  41, 42.

## Finding 5 — vector 35 conflicted with fail-fast incompatibility

**Fix: the two situations are split and the rebuild claim is removed from the
incompatible one.**

Reference §4.3 now states them as distinct rows, and decision §6 mirrors it:

| Situation | Outcome |
|---|---|
| current resolved toolchain fails Stage A (unavailable, prerelease, untrusted, outside the requirement, outside `compatibility`) | fails at Stage A. Cache lookup never reached, no candidate consulted, nothing rebuilt, no mutation. |
| current resolved toolchain passes both stages and the cache candidate was built under a **different toolchain identity** | identity is in the key, so the candidate does not match: cache miss, rebuild under the current identity. |

"There is no 'cache hit with an incompatible toolchain' path to rebuild from."
Old vector 35 is replaced by positive 14 (identity-driven miss and rebuild) and
negative 45 (Stage A failure with no lookup, no rebuild, no mutation).

## The blocking defect

`internal/godriver/builddriver_positive_conformance_test.go:382-392` (commit
`fbca886`, PR #29, merged as `351db49`) drops the explicit
`filepath.FromSlash(entry.Target)` and asserts the link round-trips byte-exactly:

```go
if err := os.Symlink(entry.Target, target); err != nil { … }
if observed, err := os.Readlink(target); err != nil || observed != entry.Target {
    t.Fatalf("materialized link target = %q, %v; want exact protocol target %q", …)
}
```

Go's `os.Symlink` on Windows performs that same conversion **itself**, before
the syscall (`$GOROOT/src/os/file_windows.go`, `func Symlink`, first statement:
`oldname = filepathlite.FromSlash(oldname)`), and `os.Readlink` returns a
relative reparse target verbatim (`readReparseLinkHandle`, `SYMLINK_FLAG_RELATIVE`
branch). So removing the call is a **no-op on Windows** and the new assertion is
guaranteed to fire.

Reproduced on native Windows (DESKTOP-3PBO632, go1.25.5 windows/amd64), curator
at `origin/main` `351db49`, `CURATOR_CONFORMANCE_ROOT` = candidate `edd0721`:

```
--- FAIL: TestToolchainIdentityVectors/unsorted-directories-files-and-internal-link
    builddriver_positive_conformance_test.go:267: materialized link target = "..\bin\go", <nil>; want exact protocol target "../bin/go"

# minimal probe
READLINK="..\bin\go" err=<nil> want="../bin/go" match=false
```

Full log: `TASK-260823-czs1cx_windows-verification.log`.

## Why the diagnosis picked the wrong side

The results artifact says "Curator's conformance materializer changed the
published symlink target … before hashing it". The materializer was only doing
redundantly what the platform does unconditionally. A Windows host **cannot**
hold a symlink whose stored relative target bytes are `../bin/go` through the Go
API at all.

The real guilty code is the fingerprint, not the materializer:
`internal/godriver/fingerprint.go:198-220` stores `record.link = target` — the raw
host-native `os.Root.Readlink` output — and hashes it into the
`curator-go-toolchain-v1` preimage. That makes the toolchain content digest
host-dependent, which contradicts what the protocol publishes: the candidate
preimage (`preimage_base64` of the `unsorted-…-internal-link` case) carries the
9 bytes `../bin/go` with no platform variance. The vector is right; the
implementation hashes host separators.

## Required rework (→ to-dev)

1. Normalize the link target to the protocol's slash form **in the fingerprint**,
   before validation and hashing, so the toolchain identity is host-independent.
   Do it in a build-tagged helper (windows: `filepath.ToSlash`; unix: verbatim) —
   a blanket `ToSlash` would rewrite a legitimate backslash inside a Unix
   filename and silently change a Unix digest.
2. Keep the round-trip assertion in `materializeToolchain`, but compare through
   the same normalizer, so the test still catches a materializer that mangles the
   target while tolerating the separator the platform is entitled to store.
3. Re-verify on a real Windows host, not only macOS. The results table's
   "Candidate-root focused environment/toolchain Go tests → exit 0" and the
   "Full local candidate gate → 41 served" rows were both macOS runs, where this
   case passes trivially; the pinned default root publishes no
   `vectors/build-drivers.json`, so the ordinary `Test (windows-latest)` lane
   skips both owned tests and cannot catch this. A native Windows host is
   reachable as `ssh win` (go1.25.5 windows/amd64) and reproduces it in ~3s.
4. No candidate regeneration is needed for this half — the toolchain preimage is
   already correct and platform-neutral. Candidate `edd0721` and its manifest
   digest stay valid; do not supersede it again for this fix.

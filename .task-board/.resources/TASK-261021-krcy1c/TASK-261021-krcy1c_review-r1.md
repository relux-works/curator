## F1: context module selection is undefined

Priority: **P1**. Location: `cips/CIP-0002-project-context-in-managed-launches.md:312`, with the manifest definition at lines 328-338 and rendering-order claim at line 314.

The brief requires the smallest executable leaf-1 grammar to be closed for an approved context item and one launch. The new context payload is exactly `{snapshot_ref, snapshot_sha256}`. The referenced manifest contains only `{version, files:[{path,size,sha256,mode}]}`. These fields bind an inventory, but never select entry modules, distinguish root content from imported supporting files, or define intra-item rendering semantics. Only the skill arm explicitly inherits an existing package/manifest contract. The ordered generation list fixes order between items, not the missing selection within this item. The later materialization hash records an output after choosing it; it does not specify which output was authorized by the item semantics.

Reproduction: retain one `project-item/1` of type `context`, environment `codex_cli`, with a validly shaped snapshot containing `entry.md` and `reference.md`, both ordinary LF-terminated UTF-8 Markdown, mode `0600`, exact sizes and SHA-256 hashes. The same item/manifest/approval bytes can be interpreted as loading only `entry.md` with supporting content retained, or loading both files as root context. Their output hashes differ. No closed member, required conventional manifest or explicit fixed rule in the candidate chooses between those interpretations. An arbitrary snapshot also has no stated context-specific Markdown validation/entry convention. This is a design counterexample, not a claim that either interpretation passed a nonexistent project implementation.

Required fix: define the context arm's admitted entry/module semantics before calling leaf 1 executable. Either explicitly require an existing closed context manifest and its module byte/ordering rules, or define a minimal closed context entry list (or a single-file subset) with deterministic loading, support-file/import closure and validation rules. Bind that choice into the approved item and add a positive context witness plus negative missing/ambiguous entry, support-file promotion and changed module-order witnesses. Do not infer roots from filenames or defer this choice to adapter implementation while claiming the grammar is frozen.

The independent witness generator and its JSON output are retained outside the repository as `.temp/krcy1c-context-witness.py` and `.temp/krcy1c-context-witness.json` in the reviewer lane. They demonstrate equal input identity and differing candidate output hashes; they do not masquerade as a production project validator.

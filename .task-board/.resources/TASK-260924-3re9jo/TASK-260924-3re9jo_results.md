## Key findings

1. Schema 2 is not enabled by default in Curator main. The operator-only exact value CURATOR_DRAFT_SOURCES_V1=1 selects draft support. With the variable unset or any value other than 1, schema 2 is refused before the frozen v1 lane is entered; schema 1 remains on the frozen path.
2. “Explicitly supports” means a reader claims and implements the whole Skillfile sources extension plus existing core, registry, audit, assurance, and manager requirements. It does not mean merely parsing schema 2. Transport revisions are separate capabilities: a revision-1-only reader rejects revision-2 policy before I/O, and a revision-2 reader also accepts revision-1 policy with revision-1 semantics.
3. The spec text must be promoted before calling the extension released. Both protocol files, their schema/conformance namespace, and public cross-references still say unreleased/draft. This promotion is already assigned to STORY-260924-15f1yi; do not create a duplicate promotion story.
4. Curator's corpus is behind current curator-spec main. The spec added install-marker-v5/valid-no-builds.json and corrected the bytes at install-marker-v5/valid.json. The diff from the Curator pin changes exactly conformance/draft-sources-v1/index.json and those two marker fixtures; protocol text, semantic-cases.json and snapshot-cases.json are unchanged. The Curator-side pin bump remains necessary after the spec release tree stabilizes.
5. Live, previously reviewed residuals are: local go-v1 marker raw-shape/tag value validation; production-entry test isolation for wrong-repository-only and wrong-commit-only registry evidence; ambiguous registry revocation/hash terminology; current-policy endpoints being bypassed on successful fetch of an existing checkout; and the undefined scp-alias-plus-port rendering. The four earlier semantic xfails named in the task brief are not still active on current main: the alias-resolution test now drives project resolve, the user insteadOf case is present, registry exact matching is wired, and the external substituted-field case is driven. The current test map has no call to semanticOutcomeKnownGap; only capture-mutation is an explicit semantic bound.

## Curator schema-2 gate and meaning of support

- Gate: internal/install/draftsources.go:20-24 defines CURATOR_DRAFT_SOURCES_V1 and checks only the exact string 1. cmd/curator/project_resolve.go:67-85 parses the switch and gives an explicit refusal when resolve/refresh is requested without it. internal/install/install.go:390-405 refuses schema 2 with “requires the draft lane” when the option or environment does not enable it. install and status accept only the locked draft workflow when enabled; cmd/curator/draft_help.go:28-45 documents the five existing verbs: project resolve, install, status, project refresh, then install of the refreshed lock. There is no separate draft command.
- The opt-in boundary is operator-owned; package data cannot enable or inspect it (internal/install/draftsources.go:20-24).
- Spec support condition: protocol/skillfile-sources.md:9-11 explicitly requires support before a schema-2 reader accepts it, and preserves all other core/registry/audit/assurance/manager requirements. Detailed requirements include selectors and closure, physical isolation, frozen local snapshot and lock, marker 5/receipt 3/source audit, status/repair, evidence, assurance, stable diagnostics, and rollback.
- Transport support condition: protocol/repository-transport.md:10-14 requires separate explicit support for each revision; revision 1 MUST NOT accept revision 2. Sections 5-7 define revision-2 identity, endpoint, alias, fallback, secret, provenance, compatibility, and strict-build rules.
- A protocol release does not itself make Curator claim support or remove its operator gate. STORY-260924-3eywt2 separately owns the default-on decision. Its acceptance must verify full conformance, not treat spec promotion as proof of implementation.

## Deliverable
1. Page parsing: `records-response-v2` (and `log-response-v2` where the
   client reads `/v1/log`) — exactly `records`, `next_cursor`, `boundary`;
   the boundary is the complete signed snapshot object
   (`registry-snapshot-v1`, all fields including `sig`), verified with the
   same §2 verification the snapshot path uses (that registry's pinned keys).
2. Chain rules in §9.3 order, before any record of a page is used:
   (1) missing or unverifiable boundary → `registry_page_boundary_missing`;
   (2) a later page whose boundary is not byte-identical to the first page's
   → `registry_page_boundary_mismatch` (precedence: missing over mismatch;
   later pages never advance or re-check the high-water);
   (3) the first page → §5 rules against the persisted high-water of that
   registry URL: version below, or equal with a different
   `head`/`merkle_root`/`log_size` → `registry_page_boundary_stale`; equal
   with the same body → accepted, nothing persisted; higher → persisted
   atomically (existing §5 discipline, same state file) BEFORE the page
   contributes. The read-only fetch variants verify but never persist.
3. A rejected page contributes nothing: the registry is excluded from that
   operation exactly like a reachable registry with an invalid snapshot
   (§5), the diagnostic names the registry URL, rollback state is left
   untouched, and the record cache is not written from a rejected chain
   (state what you do with a pre-existing cache entry and why).
4. Read-only status posture: per trusted registry URL the persisted
   high-water (`version`, `log_size`) and whether the last page boundary
   received from that registry was verified — as rows in the existing
   status machinery of `cmd/curator`, in the closed row order the landed
   union established (the S6 shell-hook block first, then the §12 posture
   block); `--check` semantics stated and tested. Persist the
   "last boundary verified" fact next to the high-water state (same atomic
   publication), never in the record cache.
5. Tests: unit tests per branch (all nine `page_boundary_cases` outcomes,
   the precedence pairs, read-only never persists, atomic persistence
   happens before contribution, cache not written on rejection) using the
   httptest registry pattern of `internal/registry/registry_test.go`; a
   conformance test executing `vectors/registry-client.json` →
   `page_boundary_cases` from `CURATOR_CONFORMANCE_ROOT` (skip only when the
   variable is unset, like `internal/closure/conformance_test.go`); if a new
   case is platform-bound, add the ledger row per `docs/ci-gates.md` — an
   unclassed skip fails the gate. Run the full suite at the rc.12 root and
   quote exit codes.
6. Docs: `docs/cli.md` (status rows, `--attest` behaviour on a rejected
   page), `docs/troubleshooting.md` for the three diagnostics, and a
   `CHANGELOG.md` Unreleased entry naming them and stating the direct

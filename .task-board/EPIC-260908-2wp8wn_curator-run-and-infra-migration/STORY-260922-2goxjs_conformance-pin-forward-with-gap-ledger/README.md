# STORY-260922-2goxjs: conformance-pin-forward-with-gap-ledger

## Description
Stop making the conformance pin wait for a whole epic. Today SPEC_PIN can only move to a spec commit whose every published case curator already implements, because consumers like internal/config TestManagerConfigV2Vectors render EVERY published case: spec main is 15 commits ahead of rc.12 and 122 of those cases belong to E1 (STORY-260916-ioemse) plus 139 to the 0017/0018 adoption, so the pin is frozen until the operator's security series lands. The repository already has the mechanism that solves this, in internal/crossconformance/draftsources_semantic_test.go: every case is classified driven / known-gap / bound / skipped, the four counts are tallied and the total is asserted against the expected case count, so nothing can silently disappear. Generalise that to the published-case consumers and move the pin forward with an attributed gap ledger: each not-yet-implemented case is a known-gap row naming the board element that owns it, the counts are pinned, and a case that starts passing FAILS the gate until it is moved out of the gap list. Effect: the dotfile-manager table (802caee), the marker-v5 fixture (8e65374) and the 0017/0018 vectors become executable immediately, and every security-series landing flips its own rows from known-gap to driven without touching the pin again.

## Scope
curator: the published-case conformance consumers (internal/config manager-config-v2 and system-config-v2 vector tests and any sibling that renders every published case), a committed gap ledger with per-row ownership, the gate wiring that pins the counts, SPEC_PIN in .github/workflows/ci.yml, docs. No spec change, no product behaviour change: a gap row records that curator does not yet implement a published case, it never weakens an implemented one.

## Acceptance Criteria
1) every published-case consumer classifies each case driven|known-gap|bound|skipped, tallies the four counts and asserts their sum equals the published case count, so a vanished case fails the gate; 2) a committed ledger lists every known-gap row with the board element that owns it and a one-line reason; 3) a known-gap row that starts PASSING fails the gate until it is removed from the ledger (the ratchet), proven by a test; 4) SPEC_PIN moves to the chosen spec commit with the ledger filled from the real failures, and the hosted matrix is green; 5) docs state that a gap row is an owed implementation, never an accepted deviation

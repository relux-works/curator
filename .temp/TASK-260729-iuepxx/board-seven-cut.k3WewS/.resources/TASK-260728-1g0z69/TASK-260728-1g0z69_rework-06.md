## 1. The finding was not hypothetical — reproduced first

The reviewer flagged that `probe/main.go:489-500` started at `cmdAccepted` and
let every unrecognised non-zero `go build` result fall through to it. Before
changing anything, the open branch was instrumented over all 13 toolchain values
on both toolchains:

| Value | exit | first line | branch taken |
|---|---|---|---|
| `default` | 1 | `go: updates to go.mod needed; to update it:` | **fall-through → accepted** |
| `go1` | 1 | `go: updates to go.mod needed; to update it:` | **fall-through → accepted** |
| `go1.99.0`, `go1.99rc1`, `go1.99.0-custom`, `go1.99.0-bigcorp` | 1 | `cannot find "…" in PATH` | recognised → accepted |
| `go1.23/../evil`, `go1.`, `go1.99.0rc1x`, `go1x`, `godefault`, `1.23.4` | 1 | `invalid toolchain "…" in go.mod` | recognised → rejected |
| `go2.0.0` | 1 | `invalid GOTOOLCHAIN "go2.0.0"` | recognised → rejected |

Identical on Go 1.25.1 and Go 1.25.5. So **four of twenty-six** toolchain
measurements were already being scored as upstream acceptance by a branch that
measured nothing, and the outcome doing it — module tidiness — has no relation
to whether a toolchain name is representable. The agreement check could not
catch it, because the fabricated verdict agreed with the isolated one.

`go build ./...` produces that outcome because it runs the **module loader**
after `toolchain.Select`. `toolchain default` and `toolchain go1` both leave the
`toolchain` line redundant against `go 1.23`, and the loader refuses to proceed
in `-mod=readonly`. Confirmed by rerunning the same module with `-mod=mod`: exit
**0**, and the rewritten `go.mod` has the `toolchain` line dropped.

## 2. What changed

### Probe (`.temp/TASK-260728-1g0z69/probe`, attached)

**Command narrowed.** The `toolchain`-position corroborating command is now
`go version` under `GOTOOLCHAIN=local+path`, not `go build ./...`. `go version`
runs `toolchain.Select` and then prints a string, so its entire failure surface
is that selection — which makes exit 0 a measurement of acceptance instead of a
report that nothing else went wrong. Read from this host's
`$GOROOT/src/cmd/go/internal/toolchain/select.go`: `go version` is not one of
the commands `Select` short-circuits (only `go env GOTOOLCHAIN`, `go env -w
GOTOOLCHAIN=…`, `go env GOMOD` and `go env GOWORK` are), and measurement
confirms it — `go env GOMOD` exits 0 for all 13 values including `go2.0.0`,
`go version` reproduces every selection outcome.

**Fourth state added.** `cmdUnknown` is not a verdict, it is the absence of one.
Any outcome that reaches it fails the probe, whatever the isolated measurement
said, and the agreement check is skipped for that row rather than being fed a
fabricated verdict.

**Recognition closed and structural.** Both classifiers are now total maps from
outcome to `{accepted, too-new, rejected, unknown}`, drawn from upstream's own
`Fatalf`/render forms, and every version-bearing form must echo the exact value
under test in upstream's own quoting:

| Position | Recognised | State |
|---|---|---|
| `toolchain` | exit 0 | accepted |
| | `go: cannot find "v" in PATH` | accepted |
| | `go: invalid toolchain "v" in <file>` | rejected |
| | `go: invalid GOTOOLCHAIN "v"` | rejected |
| | anything else | **unknown → fail** |
| `go` | exit 0 | accepted |
| | `v requires go >= v (running go …)` | too-new |
| | `invalid go version 'v':` | rejected |
| | `panic: go: internal error: missing go root module` | rejected |
| | anything else | **unknown → fail** |

Matching is per diagnostic line after stripping cmd/go's own `go: ` prefix, so a
recognised form has to be the whole of one diagnostic rather than a substring of
arbitrary output. Requiring the echoed name is load-bearing beyond tidiness:
`Select` renders two further messages with the same `invalid GOTOOLCHAIN %q`
lead that quote the **environment** value (`local+path`), never the `go.mod`
name — those now go to unknown, which is correct, because they are not
statements about the value under test.

The `go`-directive classifier is closed for the same reason even though the
reviewer only flagged the `toolchain` one: its old fall-through named
*rejection*, which launders an unrelated failure just as effectively for any
value the isolated measurement already rejects, where the two would again agree
for the wrong reason.

**New expected-red control** `-red unrelated-command-failure` restores the
retired `go build ./...` form for the `toolchain` position. It injects a real
unrelated non-zero failure — the one measured in §1 — for two shape-valid,
isolated-representable names, rather than fabricating an error string.

## Findings that constrain the implementation

1. **#101 needs a corpus revision, not just removal of an allowlist.** Preserve the strict vector and add conditional opt-in cases: tested/silent, future/warn once per operation (family, launcher, tested set), future/strict refusal, untested older/gap refusal, below-floor refusal, numeric ordering, and malformed version/probe or mutated identity refusal. The warning path must still reach every bootstrap, fingerprint, offline graph and worker check. A test double reporting a future version proves policy routing, not the safety or qualification of an actual future compiler. Both `go-v1` and `go-repository-v1` use the same toolchain boundary ([Core `:980`][s-repo-driver]; [install `builddeps.go:182`][c-builddeps]). The implementation's tested set is one family, not a generic claim of all Go ≥1.23.

2. **#106's proposal has two selection ambiguities to resolve.** Its `auto` table says “tested family,” while the detailed order also admits future families under #101. Its `path` mode is not curator's current behavior: curator selects `CURATOR_GO`, then `GOROOT`, then the compiled-in Go root, never PATH. A missing configured root and a present invalid/tampered root must not share an automatic fallback. Provisioned identity equality is per platform/distribution: different OS/architecture distributions and targets cannot promise one shared cross-platform cache key ([selector][c-selection]; [receipt input `pipeline.go:701`][c-receipt]).

3. **#107 changes what can execute before identity is established.** The issue's own one extra `env GOROOT` call is outside the present fixed bootstrap contract. Executing an arbitrary operator shim may involve an interpreter, version-manager config and child processes outside GOROOT. Private HOME/empty PATH can also make ordinary shims unable to locate their configuration/interpreter; compatibility was not established here. No implementation may quietly inherit package-local version files or general ambient HOME/PATH to make a fixture pass. A later fingerprint cannot retroactively constrain a wrapper that already ran ([Core bootstrap][s-go]; [Core identity][s-tool]).

4. **#108 reuses ideas, not an already-approved tool registry.** Audit signatures/freshness/rollback have a defined contract ([registry `:53`, `:188`][s-registry]); a tool snapshot needs its own identity, authorization and replay semantics. Organization revocations/denies must be evaluated before “first registry layer wins,” so built-in entries cannot bypass a deny. Registry signatures and verified upstream provenance are distinct evidence. A store path made only of id/version/platform is not itself a content-addressed identity; the sealed object/index must bind the digest. Version-compatible system executables do not prove identical bytes or a safe version-probe execution boundary. The aqua mirror/resolver is a proposal, not an adopted dependency or verified catalog-coverage claim in this research.

5. **#109 must distinguish unreachable from unknown.** `ls-remote` returns advertised refs, not every ancestor; a commit absent from the tip list may still be reachable. This follows from the separate ref-listing and history-traversal contracts in the primary [git-ls-remote documentation](https://git-scm.com/docs/git-ls-remote#_description) and [git-rev-list documentation](https://git-scm.com/docs/git-rev-list#_description). A later remote check must name the observed ref snapshot and inspect enough validated history to establish its result. Network/auth/read errors, truncation, shallow history, detected ref races or exhausted bounds produce **unknown/inconclusive**, never a fabricated unreachable warning. A proven result is relative to that captured advertisement; it cannot establish absence from hidden refs or predict server garbage collection. Successful object-ID fetch is evidence of availability, not reachability. Tag SHOULD is authoring guidance with valid untagged exceptions, not a new schema rejection.

6. **Equal trees do not preserve all trust identities.** For #109, matching tree objects under the same object format establishes the same Git tree, and comparing the validated `curator-build-source-v1` snapshots establishes the same admitted build bytes. Repinning still changes declared/effective commit identity in the receipt/cache input ([`pipeline.go:682`][c-receipt]). Require an explicit maintainer change and the applicable audit/provenance checks; do not adopt the issue's unconditional “no re-audit” implication or automatically repin during status/install.

7. **#110 requires Git indirection as well as name scoping.** Existing output roots already avoid blanket `.claude`-ancestor rejection; the cited code is not evidence that curator reproduces that original symptom. The residual is the complete owning-scope identity set, especially a `.git` file targeting a differently named external directory. Specify bounded byte parsing: exact `gitdir: ` prefix, strip terminal CR/LF only, preserve internal bytes including U+2028, resolve relative paths from the gitfile directory, reject NUL/malformed/unreadable pointers, then resolve and pin physical identities. Cover individual and collection selection, external adapter symlinks, aliased Git metadata, Windows junctions and a post-preflight retarget. Keep input pruning and publication-time rechecks. This is a source-boundary change; it does **not** relax the distinct external build-repository ban on local gitfiles/worktrees ([Core `:1370`][s-local-build]).

8. **#112's acquisition evidence is not a first-write proof.** Curator's acquisition function already returns a terminal commit and rejects a tag-object OID used as a commit lock through equality/type checks. The production path receives that lock from the manifest; the generic skill-source lock resolver is another path, not a writer of `build_repositories.*.locked_commit`. Add lightweight, one- and two-level annotated, 16/17-boundary, repeated-object, terminal-tree/blob, outer-name/type mismatch and existing-tag-object-lock cases. Drive the actual lock-writing entry point in whichever client offers it and curator's real acquisition entry for replay. Remediation must distinguish upgrading to a corrected skill declaration from repairing a client-generated lock; `upgrade` must not silently mutate author-owned manifests. The issue's Windows batch-wrapper anecdote was not reproduced on this Darwin host; bounded raw-object peeling avoids depending on it.

## For Ivan — three decision cards

**I1 — #106: should managers provision Go, and with what default/replay promise? NEEDS-IVAN.** Options are (A) keep operator-installed Go and improve guidance, (B) permit opt-in manager provisioning with release-pinned distributions, or (C) make automatic provisioning the normal path with historical lock replay. Recommend **B**, after rc.14: normative **MAY**, explicit managed opt-in, current explicit-selection behavior by default; common negative conformance cases for hash mismatch, unsafe archives, mutation and offline misses, but distribution pins remain reviewed manager-release data. Ship the newest supported patch per tested family and retain already referenced older installations; do not promise indefinite old-download availability. Keep toolchain identity in existing receipts initially; recording a provisioning version in portable locks and exact-version replay is a separate future schema decision with csk. If auto is later chosen, settle tested-only versus future-with-warning selection and never hide an invalid configured selection behind a download. This answers the issue's four owner questions: MAY; refusal vectors yes, universal pin list no; newest patch plus referenced retention; no new toolchain lock field in the first slice. Ivan's decision is scope/default and maintenance obligation. **ivan-cocoa's shared toolchain-preflight question remains open per the assignment** and must be reconciled before a common contract; this triage does not settle it. #106 stays unimplemented.

**I2 — #108: should the product own binary-tool distribution and registry operations? NEEDS-IVAN.** Options are (A) retain presence-checked system tools, (B) introduce a small registry-only provisioned-tool lane, or (C) implement the full built-in/organization/local-approval and verified/prompt design. Recommend **B**, after rc.14, only if Ivan accepts operating the publisher and its security/update responsibilities. For the five explicit questions: use a separate versioned `dependencies.tools` declaration; define protocol-owned stable identities with an explicit aqua mapping rather than making upstream resolver semantics the wire format; ship a small pinned built-in snapshot and allow signed organization snapshots; resolve/verify upstream artifacts in the registry publisher, not on each client; use provisioned copies for constrained tools initially, leaving existing `system` presence checks separate. Initial clients should consume flat signed records, exact digest locks and scoped paths, with deny/revocation precedence, rollback/freshness and bounded extraction tests. Defer client-side on-demand resolution, interactive trust weakening and arbitrary system version probes. Same-alias global/profile conflicts must reject or require an explicit scope choice, not select whichever skill ran last. Decide the product scope, trust policy and service owner before any implementation; then coordinate spec/curator/csk and registry consumers. #108 stays unimplemented.

**I3 — #107: may a manager execute an un-fingerprinted shim to discover Go? NEEDS-IVAN.** Options are (A) retain direct-root configuration and give operator-side resolution guidance, or (B) add an explicitly enabled discovery boundary that can execute a bounded, operator-selected shim once before admitting the real GOROOT. Recommend **A for rc.14**; consider B only after Ivan approves its changed trust surface and csk agrees the preflight contract. The current spec expressly excludes user PATH and wrappers and fixes bootstrap vectors, so the issue's “trust model does not change” claim is false for curator's baseline. If B is chosen, the contract must pin selection and interpreter/process/environment rules, private working directory, output/time bounds, refusal of package-controlled candidates and targets, at-use rechecks, and no rerun of the shim. Test real supported shims on the supported hosts under that exact environment; a mock response cannot establish compatibility. Do not widen ambient inputs or add silent PATH fallback in implementation to compensate for an unresolved contract.

These are the only owner escalations. #101 is a delegated optional permission with curator's existing refusal default retained; #109–#112 can be scoped from existing identity and execution rules without another product decision. No implementation permission is requested by this research handoff.

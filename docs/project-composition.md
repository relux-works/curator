# Derived project composition

`internal/projectcontext` composes an explicitly admitted project generation
with the registration's selected profile lock. This is a derived record, never
a replacement lock or a selection of machine-current state. The implementation
follows CIP-0002 and `protocol/project-context.md` sections 2 through 4.

`Store.PreviewComposition` reads protected admission, exact retained snapshots
and the complete selected profile closure. It returns the composition record,
generation, ordered module and skill plan, generated bytes, and materialization
receipt. It creates no lease, composition allocation or managed-home output.
Profile closure verification uses the existing profile store boundary and pin
checks before and after capture; commit members are read from their pinned Git
objects without fetching or repairing.

In `strict` mode, root context is the profile's monolithic document followed by each admitted
project context document in generation order. Empty documents are skipped, and
exactly one additional LF separates non-empty documents. System modules retain
their separate channel and joining rule. An environment without the necessary
system channel refuses. Claude Code, Codex and Muse use their registered
instruction paths; this renderer does not qualify a native adapter.

Source mode is bound into the closed registration and composition records and
therefore their identities. `Register` defaults to `strict`; the explicit
protected operator operation `RegisterMode` may select `native-project` when
allocating a new registration. Existing registrations cannot silently change
mode through `ComposeRequest`; a mismatched or unknown mode refuses. Missing
mode in retained state refuses rather than upgrading old authority. This lane
adds no in-place mode switch or lease/busy-update bypass. `project inspect`
reports this source `mode` separately from item `admission: "off"`; a
`native-project` registration always includes the exact notice
`project sources not isolated`, including before any items are approved.

In `native-project`, the managed root and system documents contain only the
selected profile. Selected project context items refuse
`project_context_unsupported`, even when optional; operators must explicitly
choose a generation without them. Disabled optional items retain the existing
`disabled` omission. Whole skills and the existing MCP delivery boundaries
remain unchanged. The non-wire `ProfileDocuments` and
`ProfileDocumentReceipt` outputs expose protected profile-only bytes and their
file inventory separately from the complete composed files. Adapters must
report **project sources not isolated** at status/launch; this renderer launches
no provider and does not claim source isolation.

Adapter contracts carry a sorted unique `modes` advertisement. Both modes need
permissions and memory-off; strict additionally needs native-source-exclusion.
These are synthetic admission contracts, not native certification. Strict file
bytes and file-inventory entries retain their existing rules; the newly required
record/adapter mode fields necessarily change enclosing record and receipt
identities. Old records are not silently rebaselined. Frozen launch carriers
remain unchanged; this package emits none.

Skills use derived v2 content pins over their complete selected snapshots;
the selected profile lock independently retains commit provenance. Identical
pins deduplicate. A different same-identity project skill replaces the entire
skill, including context, commands and requirements. Required providers and
command exports are rechecked after replacement, across the complete effective
profile closure and admitted project skills. Command collisions refuse. The
first leaf permits at most one effective command. Build and system commands
without their owning artifact activation evidence refuse; retained script
bytes are inventoried without execution. No build-cache key is invented.

Same-ID MCP definitions deduplicate only when their normalized definitions
agree. A differing definition refuses without explicit replacement approval.
The current I-REG admission rejects required unsupported MCP/transitive skill
items and names optional unsupported omissions. Composition adds no admission
arm or replacement-approval bypass around that boundary.

`Authority.PublishComposition` requires the exact preview digest, current local
manager principal, and the invocation's CWD registration. It recomputes under
the manager lock before retaining an immutable record and supporting metadata.
The composition record stays exact to `project-composition/1`; referenced policy
and materialization hashes bind ordered modules, effective skills, command
owners, adapter release, concurrency contract and every generated path's
SHA-256, byte size and logical mode (`0600` or `0700`). Generated paths exclude
native mutable state, credentials and source-worktree files.

`Resolve(ctx, held, ref, sha256)` and `Authorize(ctx, held, composition, ownerRef)`
borrow a live `managerlock.Held` witness for this exact manager home. They never
reacquire or release the caller's lock; zero, stale and other-home witnesses
refuse. The resolver rechecks the complete record digest, supporting metadata, receipt,
registration/home binding, protected bytes, current item approvals and owner
principal. Changed or unreadable evidence refuses without replacing the
baseline. This entry point admits only the local manager principal; a future
agent-grant entry point must independently enforce its live grant and ceiling.
The separate lease integration publishes the returned generated bytes and
verifies the receipt. This package starts no provider and implements no lease. Until the reviewed
I-LEASE package lands, its result types and revocation sentinel are mirrored
locally with the agreed exact field shapes. Integration replaces those mirrors
with the owning package import; it must not introduce a reverse dependency.

## Verification

Run the package tests and bounded Go-overlay controls:

```sh
env -u GIT_DIR -u GIT_WORK_TREE go test ./internal/projectcontext -count=1
env -u GIT_DIR -u GIT_WORK_TREE CURATOR_PROJECT_COMPOSITION_MUTANTS=1 go test ./internal/projectcontext -run '^TestCompositionNarrowingMutants$' -count=1 -v
```

The production record reader runs all 57 pinned composition grammar fixtures
from curator-spec `2510171ca9e7a4a9d2b69e7b2e7ec23b6d11bb8a`. Pinned JSON Schemas independently validate generated
composition, generation, adapter and control-receipt records; a bounded invalid
memory-policy plant verifies that the schema checker rejects its intended rule.
Root joining tests independently exercise the
normative byte rule, including empty documents. Fixtures use disposable Git
repositories and operator homes. These tests provide no native qualification,
tracked-session execution, lease-liveness or broader admission evidence. Store
logs and private caches under `.temp/` and validate the full default suite in a
clean normal checkout at the delivery commit.

Command owners bind the complete audited skill snapshot, including its manifest
and declared runtime companions. The command entry's individual byte digest
remains in the generated-file receipt. Immutable composition publication retains
selection choices in approved review order with an explicit empty list, so nil,
empty and permuted equivalent requests republish the same record. A different
choice still requires its own matching preview digest; stored metadata is never
overwritten to reconcile a mismatch.

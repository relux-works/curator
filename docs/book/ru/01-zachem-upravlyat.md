# Зачем управлять окружением

Рабочая задача обычно описывает ожидаемое изменение: исправить ошибку,
проверить patch, подготовить документацию. Она редко перечисляет весь
инструментарий и правила, с которыми агент начнёт действовать. Между тем
именно эти входы определяют, какую команду он найдёт, какие инструкции
прочитает и какой MCP server сможет вызвать.

Управление окружением начинается с простого вопроса: можно ли объяснить
результат запуска, не опираясь на память о том, что когда-то настроили
в домашнем каталоге?

## Невидимая конфигурация

Рассмотрим сервис с Go-кодом. В одном checkout есть `AGENTS.md`, рядом
лежит каталог skills, в пользовательском home сохранён MCP server,
а в `PATH` остался shim от старой установки. Разработчик переключает
ветку и ожидает другого кода. Вместе с кодом могут измениться инструкции,
настройки hooks и аргументы запуска инструментов. Содержимое задачи
не изменилось, но исполняющее её окружение уже другое.

Обычный package manager фиксирует зависимости программы. Для агента
приходится фиксировать и зависимости способа работы: инструкции,
контекст skills, runtime команд, декларации MCP и правила доставки
конкретному harness. Curator разделяет агентский контекст и исполняемый
runtime, разрешает зависимости и публикует управляемые adapters и shims.

Скрытый вход опасен даже без злого умысла. Старый skill может предлагать
команду, которой больше нет. У двух машин может оказаться разный профиль
с одинаковым названием. Native конфигурация может направить инструмент
на другой endpoint. Проблема не сводится к наличию плохого текста:
неизвестен сам набор входов, к которому относилась проверка.

## Три разных вопроса

Управляемое окружение должно отвечать на три вопроса отдельно.

1. **Что запрошено?** Манифест описывает зависимости и ограничения версий.
2. **Что выбрано?** Lock фиксирует конкретный набор и его идентичность.
3. **Что доставлено?** Marker и проверка поверхностей связывают выбранный
   набор с файлами в home или project installation.

Если в манифесте стоит диапазон версий, повторное разрешение через месяц
может выбрать более новую версию. Если уже есть lock, обычное потребление
должно воспроизводить его выбор. И даже верный lock бесполезен для текущего
запуска, если доставленный файл потом изменили вручную. Поэтому Curator
различает явное обновление и восстановление управляемого состояния.
⟦работает сегодня⟧

Например, профиль `review` фиксирует набор инструкций для ревью. Оператор
обновляет его и получает другой lock. Это изменение выбора. Если же
локально пропал материализованный файл, `repair` восстанавливает
поверхность из зафиксированного состояния, с отдельно оговорённой
миграцией старых locks. В обоих случаях меняются файлы, но основания
изменения разные. ⟦работает сегодня⟧

## Код проекта и право управлять агентом

Агент должен читать незнакомый код. Из этого не следует, что каждый файл
рядом с кодом вправе настраивать агента. Достаточно представить patch,
который исправляет функцию и заодно меняет MCP endpoint: принять исправление
и разрешить новый инструмент — разные действия.

Принятая модель project context считает управляющие файлы checkout
кандидатами. В запуск попадают только одобренные защищённые snapshots.
Нативное обнаружение неодобренных инструкций, skills, hooks, plugins,
MCP и permission settings должно быть исключено квалифицированным
adapter; без такой способности строгий запуск отказывается стартовать.
⟦решено⟧

Это правило имеет практическую обратную сторону. Просмотр diff можно
организовать как чтение инертного материала вне discovery roots harness.
Вход в само дерево кандидата требует более сильной гарантии: агентская
среда не должна начать автоматически загружать его control files до того,
как человек прочитает diff. Приёмка кода не заменяет одобрение control
context. ⟦решено⟧

Даже инертный diff может содержать текст, пытающийся убедить модель
изменить цель. Исключение автоматической загрузки закрывает технический
канал конфигурации, но не решает всю проблему semantic prompt injection.
Читаемый код и комментарии по-прежнему остаются недоверенными данными.

## Почему недостаточно скопировать home

Домашний каталог harness соединяет разные классы состояния: инструкции,
настройки, историю сессий, trust decisions и сведения о login. Побайтовая
копия всего каталога смешивает переносимые входы и изменяемое состояние,
а также может захватить секреты. При последующем обновлении непонятно,
какие файлы разрешено заменить.

Managed home решает часть этой проблемы через явное владение. Curator
знает управляемые поверхности и фиксирует их в marker. Provisioning seeds
после первоначального создания принадлежат harness; credential entries
имеют отдельные стратегии. `repair` не означает повторное копирование
всего native home. ⟦работает сегодня⟧

Само наличие отдельного home не создаёт project isolation. Действующая
схема home имеет ключ profile × environment. Два проекта с тем же профилем
и harness могут использовать один home; изменение текущего каталога
не добавляет к этому ключу checkout. Проектная размерность появляется
в дизайне Werkstatt, разобранном позже. ⟦работает сегодня⟧

## Что можно воспроизвести

Воспроизводимость здесь относится к объявленным входам и материализации.
Она не обещает одинаковые ответы недетерминированной модели. Успешный
повтор означает, например, что для одного lock, environment и формы
получены те же root-context bytes. Из этого не выводится равенство всей
сессии, native state или внешнего сервиса.

Поэтому полезный отчёт о запуске должен позволять различить выбранный
profile lock, доставленный контекст, применённый adapter и способ запуска.
Принятый exact-plan маршрут дополнительно связывает полный процесс и
snapshot с идентичностью плана. До его квалификации profile pin и fragment
hash нельзя выдавать за свидетельство неизменности всего окружения
живой сессии. ⟦решено⟧

Следующая глава раскладывает эти входы по слоям. После этого становится
видно, какую часть задачи решают профили, какую — managed home, а какую
добавляет допуск project context.

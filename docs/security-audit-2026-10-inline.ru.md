## N1. GC удаляет используемый runtime при неполном наборе ссылок

**Подтверждено. Приоритет: исправить в первую очередь; риск потери работоспособности установленных команд.**

Источник: `internal/scopes/gc.go:90`, `:97`, `:103`; публичный CLI: `cmd/curator/main.go:2274`, `:2328`.

`Collect` сначала получает набор ссылок и ошибки его установления, затем вызывает `sweepRuntime`, и только после удаления проверяет `marked.uncertain`. Предохранитель защищает build cache, но не runtime store. При повреждённом consumers.json набор runtime-ссылок может быть пустым; при нечитаемом/повреждённом install marker теряется ссылка конкретной живой установки.

Проверка `TestInlineAuditGCPreservesLiveRuntimeOnUncertainty` вызывает настоящий `run([gc], ...)`, берёт реальные production-блокировки и создаёт рабочий shim через `runtimestore.WriteBinShim`. До GC команда печатает `runtime-ok`.

| Состояние | Результат |
|---|---|
| Корректный реестр и marker | CLI exit 0, runtime сохранён, команда работает |
| consumers.json содержит обрезанный JSON | CLI exit 0, warning о неполноте ссылок, runtime удалён, запуск shim: no such file or directory |
| Install marker содержит обрезанный JSON | CLI exit 0, warning install_marker_invalid, runtime удалён, запуск shim: no such file or directory |

Это не требует исполнения вредоносного пакета: достаточно недоступного или повреждённого состояния. Повреждение consumer registry может затронуть runtime разных проектов. Тест не удалял реальные установки.

Почему старые тесты пропустили: `internal/scopes/gc_conservative_test.go:55` и `gc_test.go:292` проверяют сохранение consumer registry и отсутствие **build-cache** sweep, не сохранность используемых runtime-файлов.

Первое исправление: до любого runtime sweep прекращать удаление при неполной разметке; сохранять существующий conservative-подход к registry/consumer state. Добавить CLI-регрессии для повреждённого registry, invalid/unreadable marker и повторного GC. Не ослаблять нормальное удаление действительно неиспользуемых объектов.

## N2. Повторные ссылки на один Git blob обходят бюджет развёрнутого снимка

**Подтверждено на малом безопасном примере. Приоритет: исправить в первую очередь; риск чрезмерного потребления памяти при приёме внешнего репозитория.**

Источник: `internal/buildrepo/admission.go:716`, `:738`, `:1061`, `:1072`. Публичный вход локальной проверки: `internal/buildrepo/local.go:44`. Общий путь сетевого приёма: `internal/buildrepo/admission.go:429`.

`objectReader.read` возвращает повторный объект из cache до учёта лимита. Это ограничивает сумму уникальных объектов, но `walkTree` копирует blob отдельно для каждого файлового пути. Затем `frameSnapshot` ещё раз собирает весь развёрнутый снимок в памяти. Отдельного совокупного бюджета этих копий нет.

`TestInlineAuditExpandedSnapshotBudget` создаёт обычный настоящий Git-репозиторий и вызывает `AdmitLocal`, а не только внутренний helper:

| Состояние при MaxExpandedBytes=16384 | Результат |
|---|---|
| Один 4096-байтовый blob | Принят: 4113 байт содержимого, 4236 байт canonical snapshot |
| 64 различных blob по 4096 байт | Отказ build_repository_incomplete_source: object size limit exceeded |
| Один 4096-байтовый blob по 64 разным путям | **Принят:** 262161 байт содержимого, 263922 байт canonical snapshot |

Третий случай подтверждает увеличение расхода сверх заявленного бюджета без больших данных и без попытки вызвать OOM. Потенциальное исчерпание памяти — вывод из повторного выделения байтов в production-коде, а не наблюдавшееся падение машины.

Сетевой и локальный вход сходятся в `proveRepository`; применимость к сетевому источнику следует из кода, отдельного сетевого сценария с этим входом не запускалось. Контракт manager §11.5 в закреплённой rc.13-спецификации требует ограничивать aggregate expanded bytes и memory. Лимит количества файлов сам по себе не удерживает реалистичный общий объём данных.

Первое исправление: отдельно учитывать суммарные выдаваемые файлы, байты и размер canonical framing, проверяя предел **до** копирования/append. Сохранить лимиты уникальных объектов. Также ограничить количество посещаемых развёрнутых tree entries и проверять context при обходе; повторяемые tree DAG отдельно динамически не тестировались.

## N3. Восстановление приватного файла расширяет права доступа

**Подтверждено. Приоритет: средний; потенциальное раскрытие приватного контекста при доступных другим пользователям родительских каталогах.**

Источник: `internal/envprofile/unmanage.go:273`, `internal/envprofile/unmanage.go:378`. Создание backup сохраняет mode: `internal/envprofile/switch.go:1059`.

Восстановление загружает backup как `map[string][]byte`, теряя mode, и всегда создаёт файл с 0644. Реальный `profile use --takeover` сохраняет оригинальный файл с mode 0600 в backup как 0600, но последующий `env unmanage --restore-backups --env claude_code` восстанавливает те же байты с mode **0644**, exit 0. Обычный файл 0644 является проходящим контролем.

`TestInlineAuditUnmanageRestoresOriginalMetadata/private-file` использует только синтетический CLAUDE.md и реальные CLI install/use/unmanage. Фактического чтения чужим пользователем не выполнялось; возможность раскрытия зависит от прав родительских каталогов. Не утверждается, что восстановлены или утекли auth.json: credential paths отдельно запрещены.

Спецификация environments §8.3 прямо признаёт, что backup hand-maintained context может содержать secrets. Сохранение только байтов без исходных ограничений доступа небезопасно.

Первое исправление: сохранить тип и mode backup-entry в плане восстановления, использовать защищённую атомарную запись, не расширяющую исходные права. Регрессии: 0600, обычный 0644, executable mode при поддерживаемом типе; права проверить на Unix, Windows ACL отдельно.

## N4. Curator не может восстановить backup ссылки, который сам создал

**Подтверждено. Приоритет: средний; сломанный возврат к прежнему управлению контекстом.**

Источник: создание ссылки в backup — `internal/envprofile/switch.go:1032`; безусловный отказ чтения такого backup — `internal/envprofile/unmanage.go:260`.

При takeover чужой symlink Curator корректно сохраняет **саму ссылку**, не читая/перезаписывая её цель. Однако `readBackupTree` допускает только regular files. После успешного takeover обычная команда `env unmanage --restore-backups` не может прочитать собственную резервную копию.

`TestInlineAuditUnmanageRestoresOriginalMetadata/foreign-symlink`: исходный CLAUDE.md — ссылка на временный внешний файл; profile install и profile use --takeover успешны; backup имеет тип symlink; восстановление завершается exit 1 с `environment_backup_record_unreadable: backup entry is not a regular file`.

Это **не повтор E5** из сентябрьского аудита: E5 касался записи через symlink и повреждения внешней цели. Здесь takeover защищён, но обратная операция не поддерживает созданный им формат backup.

Первое исправление: согласовать типы поддерживаемых backup и restore, восстановить сохранённую ссылку как entry атомарно и без перехода по её цели. Не ослаблять отказ для ссылок в родительском маршруте. Добавить полный CLI round-trip foreign symlink → takeover → unmanage restore.

## Проверки и ограничения

Новые регрессии намеренно формулируют ожидаемое безопасное поведение. На текущем коде они красные: **9 сценариев, 4 контрольных проходят, 5 демонстрируют дефекты**. Это не исправления и не «tests green».

Команды:
```sh
env -u GOROOT GOMAXPROCS=2 go test -p 2 ./cmd/curator ./internal/buildrepo -run '^TestInlineAudit' -count=1 -v
```

Результаты и точные probe-файлы приложены рядом с отчётом как task-scoped resources.

Целевые существующие тесты:
- `internal/scopes`: выбранные `TestCollect*` прошли.
- `internal/buildrepo`: выбранные raw-object, local/network parity, tree-path и local administration conformance-проверки прошли с rc.13-векторами.
- `cmd/curator`: выбранные обычные GC и `TestEnvUnmanage*` прошли.
- Первое более широкое CLI-выражение дополнительно включило `TestGCRetainsAndReportsReferencedCompiledState`; оно не прошло из-за Go 1.27, тогда как драйвер allowlist разрешает 1.25. Это ограничение среды, не новая подтверждённая ошибка GC. Никакого обхода allowlist или изменения production-конфигурации не выполнялось. Повторный узкий проход исключал именно эту build/toolchain-зависимую проверку, результат первого сохранён.

### Реальный охват

| Поверхность | Что сделано / что не доказано |
|---|---|
| GC и удаление runtime | Production CLI, рабочая команда до/после, corruption-контроли; N1 |
| Git raw-object admission | Production AdmitLocal с настоящим Git и малыми бюджетами, unique/repeated controls; N2. Тяжёлый OOM и все варианты DAG не выполнялись |
| Takeover/restore | Полный CLI round-trip для regular/private/symlink; N3/N4 |
| Transaction namespace и snapshots | Статически просмотрены проверки путей, совпадения/alias targets, immutable-cache authentication; нового подтверждённого обхода нет, exhaustive races не проверены |
| Global shim ownership и managed file writes | Статически просмотрены ownership ledger, staging, атомарная публикация и отказ ссылкам в родителях; полного нового динамического sweep нет |
| Credential helper / worker framing | Прочитаны ограничение ответа, запрет prompting, протокол с bounded frame; полной проверки секретов/межпроцессной авторизации не было |
| npm/tar input | Отсутствие локального лимита в helper не объявлено отдельной дырой: перед ним есть artifact-policy admission, требуется отдельный разбор всей цепочки |
| Linux/Windows, опубликованные релизы и соседние сервисы | В этом inline-проходе не проверены |

Старые исследования, прерванные фильтром дочернего запуска, не являются доказательствами этих выводов. Все перечисленные воспроизведения выполнены после явной просьбы пользователя работать в основной сессии. Общий вывод: обнаружены **четыре новых дефекта в трёх механизмах**, но утверждать отсутствие других проблем нельзя.
